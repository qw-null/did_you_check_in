# “打卡了吗”微信小程序产品需求文档（PRD）

**版本：** V1.1  
**日期：** 2026-10-28  
**产品形态：** 微信小程序 + 轻量 Web 运营后台  
**开发方式：** AI 辅助开发（Codex）  
**文档说明：** 沿用原文件名；V1.0 原文归档在 `docs/archive/打卡了吗小程序_PRD_V1.0.md`。

本版本统一首版规则。任务、状态、时间与身份的定义以第 8 节为准；页面、数据结构和验收不得另行采用不同口径。第 16 节记录实施前需验证的外部条件，不再悬置首版产品范围。

---

## 1. 产品概述

### 1.1 产品背景

平台签到、积分领取、礼品和优惠权益的入口分散，用户容易忘记位置、参与步骤和截止时间，也难以管理每天需要完成的任务。

“打卡了吗”整理活动信息、提供可用入口或操作步骤，并让用户自行确认完成。它记录用户的个人待办，不替代第三方平台操作。

### 1.2 产品定位

由运营核验、社区提供线索的福利活动目录与个人打卡清单。首版只在小程序内展示待办，不主动发送通知；信息服务本身免费。活动可能存在地区、新客、消费等门槛，须在加入前说明。

### 1.3 产品目标

1. 用 10–20 条可复核的活动降低寻找入口的成本。
2. 完成“发现 → 加入 → 自行参与 → 手动确认”的核心闭环。
3. 通过文字投稿、问题反馈和运营复核维护内容质量。
4. 用明确的指标验证持续使用价值，再决定是否扩展内容和变现。

### 1.4 首版不做

- 自动登录或操作第三方平台，读取第三方积分、余额、中奖或真实完成结果。
- 保证用户具备参与资格、库存、奖励到账或收益。
- 图片投稿、自定义头像昵称、手机号或真实姓名收集。
- 主动通知、订阅消息、补卡、撤销完成、每周或不定期任务、自定义日切。
- 广告、排行榜、社交互动、邀请裂变、积分商城、个性化推荐和自动采集。
- 未审核内容公开、两个已发布活动自动合并、CSV 导入导出、后台动态配置分类或周期。

## 2. 用户与使用场景

### 2.1 目标用户

- **福利收集者：** 查找活动、判断门槛、获取入口。
- **任务管理者：** 管理多个每日或一次性任务，手动记录完成。
- **活动贡献者：** 提交线索并查看审核结果。
- **内容运营者：** 录入、审核、复核活动并处理反馈。

### 2.2 核心用户旅程

- **发现：** 游客浏览广场 → 搜索/筛选 → 查看详情与门槛 → 建立身份 → 加入清单。
- **完成：** 我的打卡“今日” → 打开入口或查看步骤 → 用户自行操作第三方 → 返回并确认完成。
- **贡献：** 提交文字线索 → 待审核 → 运营新增或关联活动 → 投稿人查看结果。
- **纠错：** 详情反馈问题 → 查看处理状态 → 运营核验并更新信息。
- **管理：** 在“全部”移除活动 → 停止待办 → 保留历史；重新加入沿用原完成记录。

## 3. 信息架构与页面

底部使用微信原生三个 tab：**活动广场、我的打卡、我的**。详情、参与指引、提交活动、问题反馈、打卡记录、我的投稿、我的失效反馈、账号与数据为二级页面。

### 3.1 活动广场

自上而下展示标题、今日待办摘要、搜索框、主分类、快捷筛选、活动列表和投稿入口。游客摘要为“建立身份后管理我的打卡”，不显示虚构数量。

主分类按奖励形态划分：**全部、积分奖励、实物礼品、优惠权益**。一个活动只有一个主分类，以参与步骤直接获得的主要奖励为准；积分以后可兑换礼品的活动仍归积分奖励，不将远期兑换物当作即时奖励。无法清晰归类时由运营补充信息后再发布。

快捷筛选为“每日任务”“即将结束”，可与主分类、搜索叠加；二者同时开启时取交集。“每日”来自任务频率，“即将结束”按 §8.3 计算，不再作为互斥主分类。

活动卡片展示平台、名称、奖励摘要、主分类、任务频率、主要参与门槛、期限提示和最近核验日期。点击卡片进入详情，独立的加入按钮避免触发卡片导航。已加入显示“已加入”；已完成的一次性活动显示“已完成”。

列表规则：

- 仅展示 §8.2 定义的当前可执行活动；首版不提供未开始活动的公开预告列表。
- 搜索输入去除首尾空格，长度最多 60 字；英文不区分大小写。使用规范化后的完整搜索串，匹配活动名称、平台名称或运营关键词中的包含关系；不做分词、拼音或语义搜索。
- 默认排序为最近核验时间倒序、活动 ID 倒序；采用游标分页，每页 20 条。
- 翻页沿用同一查询条件与排序快照；新增和重排结果在刷新时展示，每页仍过滤已失效项目，客户端按活动 ID 去重。修改搜索/筛选时重置游标，避免并发响应覆盖新条件。
- 下拉刷新重新获取列表和个人摘要。无结果时保留筛选条件，提供清空条件和投稿入口。

### 3.2 活动详情与参与指引

展示活动名称、平台、奖励摘要、主要门槛、详细资格、任务频率、期限、参与步骤、来源说明、最近核验时间和风险提示。新客、地区、消费金额、会员或运费限制须在加入按钮前可见。

入口统一为四类，所有类型均需清晰的参与步骤：

| 入口类型 | 发布所需信息 | 按钮与执行方式 | 不能直达时 |
| --- | --- | --- | --- |
| `web` 网页 | HTTPS URL、平台名称、步骤 | 仅在主体和域名条件已核实且真机通过时使用“打开活动网页” | “查看参与步骤”，可主动复制已核验链接 |
| `mini_program` 目标小程序 | 小程序名称、目标 AppID、可选页面路径、步骤 | 配置合法且真机验证通过后使用“打开活动小程序” | 展示名称、搜索方式和步骤；不要求普通用户复制内部路径 |
| `platform_search` 平台内搜索 | 平台名称、搜索关键词、步骤 | “查看搜索步骤”，支持主动复制关键词 | 保留完整文字步骤 |
| `instructions` 人工步骤 | 平台名称、足够清晰的进入与参与步骤 | “查看参与步骤” | 页面内直接阅读 |

首版目标小程序只使用 AppID 与路径配置，不额外支持短链或任意第三方 App 唤起。未知 AppID 的用户线索可提交，运营无法核实直达参数时改用搜索或步骤类型，不因此要求投稿人提供精确地址。

- 每次操作按最新可执行性决定是否提供入口。暂停、结束、待核验、平台停用时只展示状态和已核验的解释，不继续打开参与入口。
- 用户主动点击后才复制内容或调用跳转，复制成功、用户取消和调用失败均有明确反馈。
- 跳转失败展示回退步骤和反馈入口。接口调用成功只表示入口打开，不标记完成。
- “加入我的打卡”和“标记完成”独立操作，不要求先发生跳转；用户可能已自行在第三方完成。
- 仍有历史详情访问资格时，展示状态并保留自己的记录；草稿和投稿正文不公开，具体可见性见 §8.2。

### 3.3 我的打卡

一级切换固定为 **今日 / 全部**，与 §18.3.2 保持一致。

**今日：** 展示 §8.5 的实时任务集合，包含“待完成 / 已完成”二级筛选和“今日已完成 C / N 项”。没有应做任务时展示“今日暂无任务”，不显示 0/0；N 大于 0 且 C=N 时展示“今日已完成”。数量随加入、移除和活动状态改变实时重算。

**全部：** 默认展示未移除的所有清单活动，筛选为“全部、进行中、一次性已完成、暂不可执行、已移除”。“进行中”指关系 active、活动当前可执行，且不是已完成的一次性活动；每日任务今天完成后仍属进行中，行内显示“今日已完成”，不能重复确认。“一次性已完成”以保留的完成记录为准；“暂不可执行”展示其余因暂停、待核验、未开始、结束、平台停用等阻断的未移除项目，并显示具体原因。已移除项目只在对应筛选与历史中查询。

每条任务显示平台、名称、任务频率、状态、适用的入口操作和完成操作。完成时间来自服务端。

手动确认规则：

- 按钮文案为“标记完成”，首次使用展示“仅记录你的确认，不代表第三方平台核验结果；首版不能撤销”。
- 完成前明确显示所属日期；若请求跨入新日期，服务端返回日期变化提示，先刷新今日列表，再由用户重新确认，不自动记到另一日。
- 成功后同步进度、全部清单和个人统计；失败保留状态并允许重试，不能仅本地切为已完成。
- 首版不提供撤销或补卡；用户误点不会改变第三方真实状态。

移除与历史：

- “全部”行内更多菜单提供移除；确认文案说明“停止后续待办，已完成记录会保留”。
- 重新加入恢复原关系；当前周期已完成状态保持，已完成的一次性活动不会重新变成待办。
- “我的 → 打卡记录”展示所有保留的完成记录，时间倒序、每页 20 条。首版不做日历、排行榜或复杂图表。
- 活动暂停、结束、移除或更名不删除记录；记录保留完成时的平台与标题快照。涉及危险内容时按 §8.2 屏蔽相关展示。

### 3.4 我的

显示默认头像与“微信用户”，不申请自定义头像昵称。游客显示身份建立入口；身份建立后显示：

- 清单活动数：`UserActivity.status=active` 的数量，包含暂不可执行和一次性已完成项目，排除已移除项目。
- 累计手动打卡次数：本账号保留的完成记录总数，不等同于奖励次数。
- 打卡记录、我的投稿、我的失效反馈、意见反馈、账号与数据、用户服务协议、隐私政策。

意见反馈使用微信原生反馈能力；发布前验证可用性，不可用时展示可复制的项目支持联系方式。账号与数据包含数据说明和注销申请入口。

## 4. 活动提交与审核

### 4.1 提交范围与表单

广场和“我的”均提供入口，写入前建立身份。投稿为文字线索，提交后只对本人和运营可见；不得直接公开。

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 活动名称 | 是 | 2–60 字，允许近似名称 |
| 平台 | 是 | 选择已有平台；选择其他时填写 2–40 字平台名称 |
| 主分类 | 是 | 积分奖励、实物礼品、优惠权益；运营可纠正 |
| 入口方式 | 是 | 网页、目标小程序、平台内搜索、人工步骤 |
| 网页链接 | 条件 | 网页类型必填，仅接受 HTTPS，最多 2048 字符 |
| 小程序名称 | 条件 | 目标小程序类型必填，2–60 字；AppID 和路径由运营核实 |
| 搜索关键词 | 条件 | 平台内搜索类型必填，1–60 字 |
| 参与步骤 | 是 | 10–1000 字；允许没有直达链接 |
| 奖励摘要 | 否 | 最多 120 字 |
| 活动期限 | 否 | 具体日期或文字，最多 100 字；未知可留空 |
| 资格与注意事项 | 否 | 最多 500 字，提示填写消费、地区、新客等门槛 |

首版不提供图片和附件。前后端执行相同校验。可按平台和近似标题提示疑似重复，由用户确认后仍可提交；发现规则变化时优先引导使用已有活动的问题反馈。

### 4.2 投稿状态与结果

Submission 仅有 `pending` 待审核、`approved` 已通过、`rejected` 已驳回；活动实体不复用这些状态。

- 待审核可由运营填写内部备注，但没有用户补充、聊天或申诉流程。信息不足时填写清晰原因驳回，允许用户修正后重新投稿。
- 通过必须关联最终活动 ID，并记录“新增活动 / 补充已有活动 / 重复关联”的处理类型。
- 用户可查看自己的原始内容、状态、提交与处理时间、对用户可见的审核说明。关联活动可访问时提供入口，否则显示当前状态。
- 驳回必须有对用户可见的原因；不得泄露内部账号、审核凭证或其他用户投稿。

### 4.3 审核与发布

1. 核对来源、真实入口、步骤、资格、奖励、有效期和收录标准。
2. 查询现有活动，确定新增或关联；用户文字只能作为线索，不能自动覆盖线上内容。
3. 运营规范主分类、`daily/once`、期限模式和入口字段，记录核验依据与责任人。
4. 新增活动满足 §8.2 发布前置条件后发布；补充已有活动需选择具体更新字段并重新核验。
5. 同一操作原子提交审核结论、关联/活动变更和审计记录；审核请求重试返回原结果。

终态投稿不允许重复审核；纠错另建审计操作。首版不合并两个已发布活动；录入时发现重复可暂停重复项，已有用户关系和记录不自动迁移。

## 5. 数据结构

采用平台与活动两级结构。枚举、唯一性及写入约束为必需项；表名可随技术栈调整。时间戳统一保存为 UTC，服务端按 `Asia/Shanghai` 计算业务日期并返回。

### 5.1 Platform 平台

- `id`、`name`、`logo_url`（可空）、`description`（可空）、`official_url`（可空）。
- `status`：`enabled/disabled`；`created_at`、`updated_at`。

### 5.2 Activity 活动

- `id`、`platform_id`、`title`、`keywords`。
- `category`：`points/gift/benefit`；`reward_summary`、`eligibility`、`rules_note`。
- `frequency`：`daily/once`，首次发布后不可修改；新一期或规则发生实质变化时创建新活动。
- `entry_type`：`web/mini_program/platform_search/instructions`。
- `entry_url`、`target_app_id`、`target_page_path`、`target_mini_program_name`、`search_keyword`：按入口类型条件必填。
- `participation_steps`：有序文字列表，所有类型必填。
- `direct_open_enabled`：默认 false，只有实际主体与入口配置验证通过才启用；`entry_tested_at`、`entry_tested_by`、`entry_test_note` 记录依据，修改关键入口字段后清空直达验证并关闭直达。
- `validity_type`：`fixed/ongoing/unknown`；`start_at`（可空）、`end_at`（仅 fixed 必填）；`validity_note` 说明未知或长期依据。
- `publication_status`：`draft/published/paused/ended`；`first_published_at`（可空）、`status_note`。
- `verification_status`：`pending/verified/failed`；`last_verified_at`、`verified_by`、`verification_evidence`、`next_verify_at`。
- `content_restricted`：默认 false，涉嫌危险内容时屏蔽公开正文和入口。
- `source_type`：`operator/submission`；`source_reference`：来源说明，不公开内部凭证；`owner_admin_id`：维护责任人。
- `created_at`、`updated_at`。

### 5.3 UserActivity 用户活动关系

- `id`、`user_id`、`activity_id`；`status`：仅 `active/removed`。
- `first_joined_at`、`last_joined_at`、`removed_at`（可空）、`updated_at`。
- 强制唯一：`user_id + activity_id`。重新加入更新同一关系；活动结束不改成第三种用户关系状态。

### 5.4 CheckinRecord 完成记录

- `id`、`user_id`、`activity_id`、`frequency_snapshot`。
- `period_key`：每日为上海业务日期 `YYYY-MM-DD`，一次性固定为 `once`。
- `checkin_date`：实际确认请求受理时的上海业务日期；`completed_at`：对应服务端 UTC 时间戳。
- `completion_source`：固定 `manual`；`title_snapshot`、`platform_name_snapshot`、`created_at`。
- 强制唯一：`user_id + activity_id + period_key`；主接口还应支持请求幂等键，以识别跨日响应丢失后的原请求重试。

`period_key` 决定能否再次完成，`checkin_date` 用于历史与当天完成数，两者不可混用。一次性活动更换日期仍命中同一唯一键。

### 5.5 Submission 投稿

- `id`、`submitter_id`、`form_snapshot`：保留原始文字字段。
- `status`：`pending/approved/rejected`；`reviewer_id`、`reviewed_at`、`review_note`、`internal_note`。
- `review_action`：通过时为 `create/update/link_duplicate`；`resolved_activity_id`：通过必填。
- `request_id`：同一用户内唯一，网络重试不重复投稿；`created_at`、`updated_at`。

### 5.6 InvalidReport 问题反馈

- `id`、`user_id`、`activity_id`、`reason`、`description`。
- `status`：`pending/resolved/unconfirmed/duplicate`。
- `canonical_report_id`：重复反馈关联主反馈；`handled_by`、`handled_at`、`handling_note`。
- `request_id`：同一用户内唯一；`created_at`、`updated_at`。

### 5.7 User、Admin 与审计

- User：内部 `id`、服务端保存的微信身份关联、账号状态、创建/最近访问时间、注销申请时间。不向客户端暴露 OpenID 或会话密钥。
- Admin：独立受控账号与管理员角色，不与普通用户写入权限混用。
- AuditLog：操作者、动作、对象、时间、请求 ID、必要的变更摘要。内容凭证、会话、密钥和敏感原文不写入日志。
- 请求幂等结果至少保留 48 小时；业务唯一约束独立长期生效。相同请求 ID 携带不同业务参数时拒绝处理，不覆盖已确认结果。
- 埋点使用 §10 的事件字典和去重键，不作为个人打卡记录的事实来源。

## 6. 反馈与内容维护

### 6.1 反馈流程

详情提供反馈入口；允许反馈链接失效、活动结束、规则变化、无法参与、奖励不准确、疑似诈骗和其他问题。补充说明最多 500 字；选择其他时至少填写 5 字。

同一用户、活动、原因在 24 小时内已有反馈时返回原反馈，并提示已收到；请求重试按请求 ID 幂等处理。我的失效反馈显示状态、处理时间和对用户可见的说明。

### 6.2 处理流程

- 普通问题在 48 小时内首次处理：核验、更新活动或给出无法确认的说明；这是首版内部服务目标。
- 疑似诈骗或危险入口进入最高优先队列，运营发现后先暂停入口并设置内容限制，再核实；工作时段内目标 2 小时首次处理，首版不承诺全天实时响应。
- 已结束活动采用 ended；入口不确定先暂停或设待核验，不急于永久结束。
- 多人反馈可关联同一主反馈；用户始终可查看自己的提交，处理结果读取主反馈的最新公开结论，不展示其他人的内容。
- 反馈数量只用于排查优先级，不能直接认定活动失效或自动结束活动。

### 6.3 收录标准

首版收录来源可复核的官方平台活动。允许积分领取、礼品领取和优惠权益；地区、新客、消费门槛、现有会员资格、运费等必须显著说明，不能把有条件权益宣传为无条件免费。

首版不收录充值返现、投资理财收益承诺、付费入群、强制邀请/分享、赌博、抽奖概率型奖励、要求第三方账号密码或不必要敏感信息的活动。需要新付费会员才能参与的活动暂不收录；已有会员限定权益可以收录并清晰标注。

只支持能按上海自然日一次确认或按本轮一次确认管理的活动；依赖特殊日切、每周或滚动周期的任务暂不收录。第三方允许每天多次参与时，本工具每日仍只记录一次，详情须说明。

### 6.4 复核制度

- 每条已发布活动必须有维护责任人、可复核来源和核验说明。某个账号核验通过不代表所有用户符合资格。
- `fixed` 活动在核验后最多 24 小时复核一次；`ongoing/unknown` 最多 72 小时复核一次，已知结束时间到期优先结束。
- 后台默认展示到期/超期复核队列。超过 `next_verify_at` 即不再视为核验有效，直接影响列表和完成接口；定时任务只同步存储状态，不承担唯一的有效性保障。
- 运营每天至少检查一次待审核、待处理和复核队列；无人维护时暂停新增发布，超期内容按规则退出可执行范围。
- 复核周期与处理时长为首版产品默认值，后续可版本化调整；不建设用户可配置界面。

## 7. 运营后台

采用独立轻量 Web 后台，首版仅一个管理员角色，账号由受控方式初始化，不开放注册。

### 7.1 首版功能

1. **工作台：** 待审核、待处理、高优先反馈、待复核、平台和活动数量。
2. **平台管理：** 新增、编辑、启停；停用前展示影响范围并确认。
3. **活动管理：** 录入、编辑、发布、暂停、恢复、结束；检查发布条件并填写核验依据。
4. **投稿审核：** 新增活动、选择更新字段、关联已有活动、驳回；公开与内部备注分开。
5. **反馈处理：** 核验、处理、重复关联和同步公开结论。
6. **操作日志：** 查询关键状态和内容变更。
7. **账号数据申请：** 查看注销请求、处理进度与完成记录。
8. **基础统计：** 展示 §10 的指标与样本量；无数据时显示无数据，不能填充假值。

分类、频率和策略作为版本化配置维护；协议与项目联系信息通过受控发布更新。首版没有 CSV、复杂角色、批量合并或通用配置平台。

### 7.2 权限与变更

所有管理接口进行服务端身份与角色校验。编辑已发布内容采用提交时校验与原子更新，不将未提交的草稿暴露给用户；关键入口、资格或规则变化必须重新核验。发布前的编辑内容保留在 draft；已发布活动不退回 draft。

并发编辑采用版本/更新时间校验；冲突时先重新读取，不静默覆盖他人更新。关键动作写审计，同一请求重试不重复执行。

## 8. 统一业务规则

### 8.1 身份与数据归属

- 游客可浏览公开活动、协议和隐私说明；个人记录只在建立身份后可用。
- 第一次加入、完成、投稿、反馈前，按微信当前能力和隐私要求建立服务端会话。身份能力与手机号、头像昵称授权无关。
- 不建设本地匿名清单和账号合并；同一小程序的同一微信身份使用同一服务端账号，跨设备同步。
- 服务端从会话确定用户 ID，并逐对象检查所有权。客户端传入的用户或角色标识不作为授权依据。
- 会话失效时保留当前表单，重新建立身份后再重试原请求；无法建立身份则停止写入并允许用户主动重试。
- 从第三方返回或切回前台时刷新服务端时间、状态和完成记录，避免使用旧日期或旧状态操作。

### 8.2 状态、可见性与可执行性

活动发布状态只有 `draft`、`published`、`paused`、`ended`。允许 draft→published，published↔paused，published/paused→ended；ended 为终态，新一轮创建新活动。未知是否结束时先暂停，避免误用终态。

核验结果独立为 pending、verified、failed。只有 verified 且 `now < next_verify_at` 才算当前核验有效；到期按待核验处理，无须等待后台任务。

定义当前可执行 `executable`：平台 enabled、活动 published、核验有效、内容未受限、已到开始时间且未到结束时间，所有条件同时满足。未知/长期期限按 §8.3 处理。这里的可执行只表示信息层面允许尝试，不能保证个人资格、库存或奖励。

| 情形 | 广场 | 详情 | 新增/恢复加入 | 新的手动确认与入口 |
| --- | --- | --- | --- | --- |
| draft 或未发布的投稿 | 不展示 | 普通用户不可访问 | 不允许 | 不允许 |
| executable=true | 展示 | 可访问 | 允许 | 入口可用；新确认另需身份、关系和周期通过 |
| 已发布但未开始 | 不展示 | 已有公开链接或个人关系可查看预告说明 | 不允许 | 不允许 |
| 核验待定、失败或超期 | 不展示 | 仅曾发布内容可查看状态 | 不允许 | 不允许 |
| paused、ended、时间已过期或平台停用 | 不展示 | 仅曾发布内容可查看状态/历史 | 不允许 | 不允许 |
| content_restricted=true | 不展示 | 只显示通用风险说明与用户自己的安全记录 | 不允许 | 不允许 |

参与入口不要求登录或已加入，只检查活动可执行性和直达配置；新的手动确认必须建立身份、关系 active 且满足周期规则。已完成任务仍可查看有效入口，但不能新增同周期完成记录。

已完成一次性活动的关系可保留/恢复，但不产生新任务。恢复加入同时必须满足 executable；不可执行的已移除项目只能查看历史。

首次发布必须满足：平台启用、字段完整、分类和周期有效、步骤清楚、已知资格已披露、期限规范、核验有效、来源和责任人齐全。可以提前发布尚未开始的已核验活动，但按表格不进入广场和待办。直达能力未验证不阻止发布清晰步骤，但必须关闭直达按钮。

曾公开的安全内容保留历史可访问性；待审核稿、内部备注和凭证不可见。受限内容的正文、链接及不安全标题快照都不返回普通用户，自己的记录可改用“活动信息已限制展示”。

### 8.3 时间与有效期

- 所有业务日期采用 `Asia/Shanghai`；客户端显示服务端返回的业务日期，不能依赖设备自行修改的日期。
- 有效时间区间为 `[start_at, end_at)`；start_at 为空表示已核验当前已开始，不能表示未知未来日期。
- `fixed`：有明确结束时刻；输入“2026-10-31 当日结束”转换为上海时间 2026-11-01 00:00:00 的排他结束边界；有具体时分时保留其精度和原意。
- `ongoing`：来源明确说明长期开展，end_at 为空；对用户显示“长期开展，需定期核验”。
- `unknown`：当前参与方式已核实，但结束时间未知，end_at 为空；对用户显示“截止时间待核实”。未来开始时间也未知的线索不发布。
- fixed 以外的 end_at 必须为空；有开始和结束时间时必须 start_at < end_at。
- “即将结束”为已开始且剩余时间大于 0、不超过 48 小时的 fixed 活动，不覆盖暂停或待核验等阻断状态。
- 时间是否过期在每次读取、加入和完成时计算。平台恢复不自动使已过期、超期未核验或单独暂停的活动可执行。

### 8.4 完成周期与幂等

| 频率 | 周期标识 | 待办条件 | 完成后 |
| --- | --- | --- | --- |
| daily | 服务端上海日期 YYYY-MM-DD | executable、关系 active，且当前日期无完成记录 | 当天不再待办；次日满足条件时恢复 |
| once | 固定 once | executable、关系 active，且整个活动无完成记录 | 永久退出待办；新一轮用新活动 |

完成请求包含唯一 `request_id` 和界面展示的 `expected_date`，不接受用户自选历史日期。服务端先按身份与请求 ID 检查既有结果，再检查目标周期已有记录；同请求重试或相同周期重复确认返回原记录，不增加计数。

首次受理时由服务端捕获时间：若 expected_date 不等于当时业务日期，返回日期变化提示并刷新，不创建记录。用户再次确认使用新请求 ID 和新日期。由此，23:59 打开、00:01 首次确认不会静默记为前一天或新一天。

对于尚未完成的新请求，在同一原子处理边界内校验当前可执行性、关系和唯一键，再保存记录。状态在请求前已变更时拒绝；与暂停并发时按服务端确定的提交顺序生效。原成功记录的重试在暂停后仍返回既有结果，不能误报为首次失败。

日切不删除/修改历史记录，不使用每天批量清空完成状态的实现。未完成的一次性活动每天仍可进入今日；已经完成的不会因跨日、重新登录、移除重加或活动编辑而重置。

### 8.5 今日集合与实时进度

对当前用户和业务日期 d：

- `U`：当前可执行、关系 active、当前周期未完成的活动。
- `C`：完成记录的 checkin_date=d 的活动；即使之后暂停、结束或移除，今天已完成事实仍保留。
- 今日列表为 U 与 C 的并集，待完成筛选为 U，已完成筛选为 C。
- 今日应做总数 `N=|U∪C|`，今日完成数 `|C|`；进度为 `|C|/N`，N=0 展示空状态。
- 未完成活动暂停/移除后退出 U；重新加入或恢复后符合条件的进入 U。界面重算并说明“清单已更新”；已完成的活动仍在 C，不丢失当天进度。
- 一次性活动在过去日期完成时，不进入今日，保留在全部与历史记录。历史完成但当前不可执行的项目不提供参与入口。

这是页面实时口径；分析指标使用 §10 的固定事件集合，不拿实时剩余待办作分母。

### 8.6 移除、复用与历史

移除只变更关系为 removed，不删除 CheckinRecord。恢复关系不新增关系、不重置 first_joined_at 或完成记录。活动标题修正保留快照；新一期、任务频率变更或奖励规则实质改变时创建新活动，不继承旧活动完成资格。

## 9. 非功能需求

### 9.1 易用性与状态反馈

- 游客浏览不弹出无关授权；写入前解释身份用途，登录失败不丢失填写内容。
- 每个入口都给出真实可执行动作。状态变化、未开始、超期核验、已结束和平台停用有不同说明。
- 普通加入无需多余弹窗；移除、结束活动、平台停用和注销需要确认。首次手动确认展示不可撤销说明。
- 列表、详情与个人摘要在写入成功后保持一致；切回前台重新校准日期和状态。

### 9.2 性能与可靠性

以下是首版验收目标，不代表已完成测试或对所有网络条件的承诺：

- 测试环境为体验版、稳定网络往返延迟不超过 100ms，种子数据 1000 条活动、单用户 100 条清单与 500 条历史记录，20 个并发请求；报告同时标明设备、网络、冷/热启动和样本数。
- 在上述环境至少采集 100 次请求，列表/详情/个人列表的服务端响应 p95 不超过 1 秒；写操作 p95 不超过 1.5 秒。外部跳转和第三方加载时间单独记录，不计入本服务指标。
- 热启动后首屏可交互 p95 不超过 2 秒；冷启动单独报告。首次展示加载态不能冒充数据已加载成功。
- 请求超时为 10 秒；只读请求最多自动重试一次。写请求由用户主动重试并复用请求 ID；表单修改形成新请求。
- 列表每页 20 条，搜索输入防抖 300ms，并抑制过期请求结果。
- 原子写入与数据库唯一约束承担一致性保证；前端 loading 和禁用仅用于体验。不得把网络超时直接当作“服务端一定未写入”。
- 自动备份至少每日一次，保留 7 个每日恢复点；内测前完成一次备份恢复演练，目标恢复到最近 24 小时内的恢复点、4 小时内恢复基本服务。备份与清理规则见 §9.4。

### 9.3 安全与内容处理

- 管理权限和个人数据所有权由服务端校验；小程序不直连具备全表读写权限的数据凭证。
- 客户端不保存数据库、微信服务端或管理员密钥；服务端凭证仅通过受控环境配置使用。
- 投稿和反馈按普通文本处理；后台不把用户原文当作可执行 HTML。公开内容必须人工审核，并按实际使用能力接入平台要求的内容处理措施。
- 网页只接受 HTTPS；运营核对官方来源、最终落地页和门槛，复制/打开仅使用已核验配置。用户提交任意链接不自动获得信任或触发服务端抓取。
- 单账号首版投稿最多 5 次/24 小时、反馈最多 20 次/24 小时，重复请求不重复计数；超限说明下次可提交时间。后台保留暂停异常账号写入的能力。
- 错误响应不暴露内部堆栈、凭证或其他用户数据；日志不记录登录临时凭证与会话密钥。

### 9.4 隐私、数据保存与注销

首版仅保存身份关联、清单、完成记录、文字投稿、问题反馈与实现稳定性所需的少量日志；隐私声明必须与实际数据、SDK 和接口一致，不预先声明未使用的能力。

数据保存为首版项目默认策略，不构成对法律或平台最低期限的判断：

- 清单与完成记录在账号存续期间保留；不上传通讯录、定位、手机号、姓名、第三方账号或截图。
- 运行日志保留 30 天、可关联用户的原始分析事件保留 90 天；去标识的汇总指标可长期保留。
- 运营审计保留 180 天，最小化记录且不含用户敏感正文；如适用规则要求其他期限，在上线核查时修订策略与隐私文本。
- 自动备份最长保留 30 天；账号删除后数据不再用于在线服务。若恢复旧备份，须在对外恢复服务前重放删除清单，不能恢复已注销用户的可用数据。
- “账号与数据”提供注销申请与二次确认，申请后立即失效现有会话、停止写入，并展示申请进度；首版不提供撤回。
- 在线个人数据在 7 个自然日内清除。已公开活动保留运营核验后的公共内容，解除投稿人关联；待审核个人稿件删除，反馈处置与审计仅保留必要的去标识结果。
- 注销处理中重新登录只允许查看处理状态；完成后再建立身份视为新账号，旧清单与记录不恢复。原始分析事件清除相应身份关联，备份随保留期到期清除。

首次内测前由负责人确认可执行的数据清理流程、项目支持渠道和隐私说明；不以只有一页政策文本作为功能交付。

## 10. 埋点、指标与验证计划

### 10.1 事件字典

所有事件包含唯一事件 ID、事件名、环境、时间、业务日期、可用时的内部用户 ID、活动 ID 与来源页面。游客不收集 OpenID，不生成可跨产品追踪的标识。开发、运营自测与明确标记的隔离测试数据不计入产品指标。

| 事件 | 触发时机与去重 |
| --- | --- |
| `activity_list_view` | 广场列表实际展示，按页面访问 ID 记录 |
| `activity_search` | 用户确认或防抖完成后的有效搜索，最多存规范化搜索词；不携带账号或其他个人信息 |
| `activity_detail_view` | 详情成功展示，生成 `detail_view_id`；记录是否可执行、是否已加入 |
| `my_checkins_view` | 已建立身份的用户成功展示我的打卡，作为核心返回行为 |
| `task_view` | 今日待完成任务行实际展示，按用户、活动、展示日期去重；只展示已完成行或未展示的分页项不计入 |
| `activity_join` | 服务端首次成功加入，按唯一关系去重；记录来源及详情访问 ID（如有） |
| `activity_rejoin` / `activity_remove` | 服务端成功恢复或移除关系，幂等重试不重复计数 |
| `entry_action` | 用户操作入口，记录详情/今日/全部来源、动作 ID 与打开/查看步骤类型 |
| `entry_action_result` | 对应动作的 opened、guide_shown、copied、cancelled、failed，不代表第三方完成 |
| `checkin_complete` | 服务端成功创建记录，以记录 ID 去重，包含 period_key 和 checkin_date |
| `submission_create` / `invalid_report_create` | 服务端成功创建，以业务对象 ID 去重 |
| `submission_reviewed` / `invalid_report_handled` | 服务端首次形成审核结论或反馈 resolved/unconfirmed 结论；后续改动另记审计，反馈合并不冒充最终处理 |

客户端展示事件不能替代服务端写入事实；服务端写事件在数据库成功后产生，允许可靠补发并按去重键消重。入口被取消或失败不会触发完成事件。

### 10.2 指标口径

按上海日历日统计，并同时展示分子、分母和样本期。所有除法的分母为零时显示“不适用”。

1. **详情页加入转化率：** 在同一个 detail_view_id 中产生首次成功加入的详情访问数 / 展示时可执行且尚未加入的详情访问数。卡片直接加入、恢复加入单独统计，不混入该分子。
2. **已展示任务完成率：** 对当日 `task_view` 的用户—活动去重集合 S，分子为其中 checkin_date 等于当日且成功完成的任务数，分母为 |S|。移除、暂停、结束不回删既有展示事件；同一任务反复展示不增加分母。未展示或仅通过其他页面完成的记录仍计入打卡总数，但不混入该指标；它不代表全部理论应做任务的完成率。
3. **详情页入口点击率：** 在同一 detail_view_id 内发生入口动作的访问数 / 当次展示有效入口的详情访问数。任务列表来源单列，重复点击同一访问只计一次。
4. **D1/D7 核心留存：** 首次成功加入活动的用户为激活 cohort；在激活后的第 1/7 个上海日历日发生 my_checkins_view 或 checkin_complete 的用户数 / 该 cohort 用户数。未满观察日的 cohort 不计入。
5. **投稿通过率：** 同期首次审核结论为 approved 的数量 / 同期首次审核为 approved 或 rejected 的数量。另展示待审数量、首次处理耗时中位数与 p95。
6. **被反馈活动比例：** 周期内曾公开且收到反馈的不同活动数 / 周期内曾公开的不同活动数；同时展示人数、反馈量和确认失效数量。该比例不是实际失效率。
7. **反馈处理时长：** 从反馈创建到首次 resolved/unconfirmed 公开结论的时间；重复反馈使用主反馈结论时间计算原用户等待时长，主反馈尚未结论时仍计入待处理，另行展示合并率。
8. **重复使用：** 激活日起 7 个日历日内，在至少 3 个不同日期产生完成记录的用户占比。每日/一次性活动的样本分开观察。

页面实时进度采用 §8.5；分析采用事件集合及记录日期，不从“当前剩余待办”反推分母。小样本必须同时展示数量，不通过百分比单独做结论。

### 10.3 小范围验证

- 先录入 10–20 条已核验活动，覆盖至少 3 个平台，并同时包含每日与一次性任务。优先覆盖已具备条件的直达与步骤入口；没有可用直达条件时全部采用步骤回退并如实标注。不足内容数量或质量标准时延后邀请，不用凑数内容替代。
- 首批观察期为 21 天，前 14 天争取至少 20 名非运营用户首次加入活动，后 7 天用于补齐 D7 观察。样本不足时延长观察，不直接判定成功或失败。
- 首版内部假设目标：成熟 cohort 的 D7 核心留存不低于 20%，首周至少 3 日完成的用户占比不低于 30%。这些是项目判断起点，不是行业基准或效果承诺。
- 同时记录用户离开的原因：内容价值、操作步骤、资格不符、入口不可用、缺少通知或误点等，结合具体反馈决定调整。
- 达到使用目标且维护成本可承受后再扩充；入口可靠性或内容供给不足时先修复这些问题，不优先上广告。

## 12. 异常场景

| 场景 | 处理方式 |
| --- | --- |
| 没有直达链接或主体不支持直达 | 使用搜索/步骤；不展示无效打开按钮 |
| 用户取消跳转或复制 | 返回原页，不提示已参与，不标记完成 |
| 跳转调用失败 | 展示已核验回退步骤与问题反馈 |
| 未开始、暂停、结束、超期核验、平台停用 | 同步原因、停用新参与/确认，不清除历史 |
| 用户重复加入 | 返回既有关系，首次加入统计不增加 |
| 当前周期重复完成 | 返回既有记录，不增加计数 |
| 23:59 打开、00:01 首次确认 | 提示日期变化、刷新、用户重新确认 |
| 完成成功但响应丢失，跨日重试 | 原请求 ID 返回原完成结果，不新建另一日记录 |
| 网络超时无法确定结果 | 提示“结果待确认”，主动重试或刷新获取服务端状态 |
| 投稿缺字段或接口失败 | 保留当前表单；错误定位到字段，重试沿用同一请求 ID |
| 投稿重复 | 提示既有活动；运营可关联，不能自动覆盖内容 |
| 平台名称选择其他 | 保存投稿的平台文字，由运营关联/创建标准平台 |
| 反馈不能确认 | 显示无法确认和理由，不虚构解决结论 |
| 会话失效 | 保留上下文，重新建立身份后重试；失败则停止写入 |
| 活动记录涉及受限内容 | 保留完成事实，用安全占位说明替换正文、链接和不安全标题 |
| 无任务或零分母 | 展示空状态/不适用，不出现 0/0 或无穷百分比 |
| 注销申请中 | 失效会话、停止写入，只允许查看处理状态 |

## 13. 验收标准

### 13.1 页面与内容

- 游客可浏览；写入建立身份后才提交，不收集手机号、头像昵称或截图。
- 广场分类、搜索、快捷筛选与分页可叠加；列表只含当前可执行活动，关键门槛加入前可见。
- 实际启用的入口类型均有可运行的代表配置；所有启用直达的配置通过真实主体真机验证，其余配置验证完整的步骤回退，不要求每类都具备直达能力。
- 今日/全部结构、实时进度、一次性已完成与暂不可执行筛选一致；“我的”可查询保留的记录。
- 文字投稿进入待审核；通过关联活动，驳回原因可见；用户只能查看自己的未公开稿件与反馈。
- 管理员可录入、发布、核验、暂停、恢复、结束与处理反馈；关键动作留审计，冲突编辑有提示。

### 13.2 业务边界验收

| 场景 | 必须满足 |
| --- | --- |
| 每日同周期重复/并发确认 | 只创建一条记录，累计次数只增加一次 |
| 一次性隔日再确认 | 不创建第二条，结果指向既有记录 |
| 跨零点首次确认 | 拒绝旧 expected_date，刷新后由用户再次确认 |
| 成功后响应丢失，跨日重试 | 同请求返回同记录；不能误增次日完成 |
| 用户切换设备 | 同一账号看到同一清单和周期状态 |
| 修改设备日期 | 不改变服务端日切、期限或完成归属 |
| 完成前活动暂停、平台停用或到期 | 新确认被拒绝，列表刷新并显示原因 |
| 状态变更与完成同时发生 | 按明确提交顺序一致处理，记录与返回一致 |
| 核验期限到但定时任务尚未运行 | 读取/写入即时阻止继续执行 |
| 已发布但未开始 | 广场和今日无可执行任务，公开详情显示未开始 |
| 未知截止与长期活动 | 文案和数据模式不同，不展示永久有效承诺 |
| 移除后同日重加 | 沿用关系及记录，不重置周期、不重复首次加入 |
| 已完成活动随后暂停或移除 | 今日 C 保留，进度不丢失已有完成；入口按最新状态关闭 |
| 任务未完成即移除/暂停 | 从 U 移出，页面 N 重算；分析不删除既有展示事件 |
| 一次性过去日期已完成 | 不重新进入今日，在全部/历史可查 |
| 投稿审核请求重复 | 只形成一个结论和关联，不重复创建活动 |
| 反馈关联主反馈 | 原用户看得到最新公开处理说明，看不到其他人的原文 |
| 账号注销 | 会话失效、处理可追踪、在线数据按约定清除，恢复备份不复活数据 |

### 13.3 发布验收

- 服务端权限、数据隔离、原子写与唯一约束符合 §5、§8、§9，不以按钮隐藏作为保证。
- 性能按 §9.2 的环境、数据量和样本报告，未达到目标时列明差距与处理，不伪报通过。
- 指标按 §10 构造小规模明确标记的隔离样本核对：重复事件不重复计数、任务移除不回删曝光、零分母为不适用、D7 未成熟样本不计入。
- iOS、Android 各至少一台真机，覆盖窄屏与大屏、系统大字体、键盘、安全区、返回前台、网络中断与入口回退。
- 已验证一次备份恢复；10–20 条活动具备有效核验与维护负责人；协议、隐私、联系渠道、平台配置齐全。
- 未实现的首版功能不能进入上线完成清单；无法验证的外部条件明确记录，不声称审核必然通过。

## 14. 开发执行约束

按 §11 的顺序小步实现，每步阅读现有代码并运行与改动相关的检查。技术选型在实施记录中说明，不在开发中默默更换。

每阶段交付包括：

1. 新增/修改文件、完成的需求条目与剩余工作。

首版数据接口的公共约定：返回服务端业务日期与可执行原因；列表采用统一分页；写入接收请求 ID。只有完成接口需要 expected_date，其他表单不能让客户端指定业务发生时间。错误码至少区分身份失效、日期变化、当前不可执行、参数不合法、限流和未知结果待确认。

## 18. UI/UX 设计规范与开发约束

### 18.1 设计目标

小程序用户端采用接近 iOS 原生应用的极简设计语言，同时兼容 Android 与微信运行环境。本节视觉约束面向用户端；运营后台可采用高效表格和标准管理组件。业务行为严格遵循第 3、8、11 节，不因视觉稿另设规则。

设计核心原则：

1. **极简主义：** 减少不必要的装饰、边框、阴影和视觉元素，突出活动内容与核心操作。
2. **内容优先：** 活动名称、奖励信息、参与步骤、打卡状态应具有清晰的视觉层级。
3. **轻量交互：** 用户应能够快速完成浏览、加入打卡、手动确认和活动投稿。
4. **统一规范：** 全部页面使用统一的色彩、字体、间距、圆角和组件样式。
5. **自然反馈：** 按钮点击、任务完成、投稿成功等操作应提供简洁明确的反馈。
6. **移动端优先：** 同时适配常见 iPhone 与 Android 设备，覆盖窄屏、大屏和系统大字体。

整体风格应接近 iOS 原生应用的简洁、精致与秩序感，但不得直接复制 Apple 官方产品的专有界面或品牌元素。

### 18.2 视觉设计规范

#### 18.2.1 色彩系统

采用低饱和度中性色作为基础，使用克制的蓝色作为主要交互色。

| 用途     | 色彩值    | 设计说明                     |
| -------- | --------- | ---------------------------- |
| 页面背景 | `#F5F5F7` | 浅灰白色，降低视觉负担       |
| 卡片背景 | `#FFFFFF` | 保持内容清晰、干净           |
| 主文字   | `#1D1D1F` | 用于页面标题、活动名称       |
| 次级文字 | `#626268` | 用于辅助说明、时间、备注     |
| 主强调色 | `#0062CC` | 用于主要按钮、链接、选中状态 |
| 成功状态 | `#207A3C` | 用于打卡完成文字，标签底色 `#EAF7EE` |
| 提醒状态 | `#8A4B00` | 用于提醒文字，标签底色 `#FFF4DE` |
| 错误状态 | `#C62828` | 用于错误文字，标签底色 `#FDEDEC` |
| 分隔线   | `#E5E5EA` | 用于列表分隔和轻量边界       |

设计约束：

- 页面中以白色、浅灰色和深色文字为主。
- 强调色仅用于必要的交互元素，不应大面积铺设。
- 不使用多色渐变作为默认背景。
- 不使用大面积高饱和色块装饰页面。
- 不应仅通过颜色区分活动状态，还应提供文字或图标说明。
- 普通正文、辅助文字和普通字号按钮文字与实际背景的对比度至少 4.5:1；状态文字使用上表深色字与浅色底，主按钮使用白字蓝底。不可用控件也应保持可辨识。该标准是本项目设计目标，不等同于微信审核结论。

#### 18.2.2 字体规范

优先使用系统默认无衬线字体，保证中文在 iOS 和 Android 设备上的自然显示。

建议层级：

| 元素         | 字号建议 | 字重     |
| ------------ | -------: | -------- |
| 页面主标题   |  26–30px | Semibold |
| 区块标题     |  18–20px | Semibold |
| 活动名称     |  16–17px | Medium   |
| 正文内容     |  14–16px | Regular  |
| 辅助说明     |  12–13px | Regular  |
| 按钮文字     |  15–16px | Medium   |
| 数据统计数字 |  28–36px | Semibold |

以上为 CSS px 参考，字号使用统一变量并尊重系统字体缩放，不因屏幕宽度机械缩放正文。间距、卡片等布局可按 375px 设计基准换算为 750rpx，即设计 1px 对应 2rpx；1px 细线、字号和安全区分别处理，不做全局无差别倍增。大字体下允许换行和容器增高，不裁切重要文字。

#### 18.2.3 间距与布局

建立统一的间距体系：

- 页面左右边距：16–20px。
- 卡片内部间距：16px。
- 主要区块之间：24–32px。
- 同一组内相关元素间距：8–12px。
- 页面底部应考虑安全区域和底部导航栏高度。

所有页面应遵循统一的对齐规则。优先使用清晰的垂直布局、自然留白和规整的信息分组。

#### 18.2.4 圆角、边框与阴影

- 普通卡片圆角：16–20px。
- 按钮圆角：12–16px。
- 标签圆角：采用胶囊形或轻圆角。
- 输入框圆角：12px 左右。
- 分割线使用低对比度浅灰色。
- 默认卡片不使用明显阴影。
- 弹窗和浮层仅使用轻微阴影区分层级。

禁止为每一个信息区域都添加独立边框，避免出现传统后台系统的密集卡片风格。

### 18.3 三个主页面的 UI 规范

#### 18.3.1 活动广场

**页面定位：发现福利活动。**

采用清爽的内容浏览布局。

页面从上到下依次为：

1. 页面标题「打卡了吗」，搭配简短的欢迎文案。
2. 今日待办摘要，显示今日尚未完成的打卡数量。
3. 搜索框，支持搜索平台名称和活动名称。
4. 主分类：全部、积分奖励、实物礼品、优惠权益；快捷筛选：每日任务、即将结束。
5. 活动列表，使用统一的简洁活动卡片。
6. 提交活动入口。

活动卡片应包含：

- 平台名称或图标。
- 活动名称。
- 一句话奖励说明。
- 主分类、任务频率与主要门槛。
- 期限说明与最近核验日期；未知截止时间明确标注。
- 加入打卡或已加入状态。

卡片应以文字信息为主体，不要求每项活动都使用封面大图。

活动卡片的主要操作应明确，但避免同时出现过多按钮。用户点击卡片进入详情页，点击主要操作即可加入打卡清单。

#### 18.3.2 我的打卡

**页面定位：管理每日任务。**

该页面应突出任务完成情况，而不是复杂的统计图表。

页面结构：

1. 页面标题「我的打卡」。
2. 一级切换「今日 / 全部」。
3. 「今日」按 §8.5 展示实时进度，例如「今日已完成 3 / 5 项」和简洁进度条；无任务不显示 0/0。
4. 「今日」内提供「待完成 / 已完成」二级筛选。
5. 「全部」内提供全部、进行中、一次性已完成、暂不可执行、已移除筛选，按 §3.3 定义筛选集合并展示具体不可执行原因。

每项任务展示：

- 活动名称和所属平台。
- 当前任务状态。
- 打开活动的操作入口。
- 手动确认完成的操作。
- 必要的参与说明。

交互规则：

- 用户可先打开外部活动页面，再返回小程序手动确认完成。
- 完成任务后，进度与任务状态应即时更新。
- 已完成任务应采用弱化显示的方式，避免干扰未完成任务。
- 重复确认按用户、活动、周期去重；一次性完成后跨日也不能新建记录。
- 每日按服务端上海日期计算；跨日期首次确认先刷新并由用户再次确认，原请求成功后的重试返回原记录。
- 已完成后暂停或移除仍保留今天的完成事实；新的入口和确认按最新状态控制。
- 移除菜单说明历史保留，重新加入不重置周期；首版不展示撤销和补卡按钮。

#### 18.3.3 我的

**页面定位：展示用户信息和个人记录。**

采用简洁的个人中心布局，不使用传统管理后台式菜单。

页面结构：

1. 默认头像与「微信用户」；游客展示身份建立入口，不申请头像昵称授权。
2. 核心数据摘要：清单活动数、累计手动打卡次数，口径按 §3.4。
3. 打卡记录。
4. 我的投稿。
5. 我的失效反馈。
6. 意见反馈。
7. 账号与数据：数据说明、注销申请与处理进度。
8. 用户服务协议与隐私政策。

数据摘要可采用横向排列的轻量数字模块，不应设计成占据大量空间的大型统计卡片。

不强制收集手机号、真实姓名等非必要个人信息。

### 18.4 通用组件规范

开发时应建立可复用的组件，避免三个页面重复实现相似样式。

建议至少包括：

- `PageHeader`：统一页面标题。
- `ActivityCard`：活动卡片。
- `CategoryTabs`：活动分类切换。
- `StatusTag`：活动状态标签。
- `PrimaryButton`：主要操作按钮。
- `SearchBar`：搜索框。
- `ProgressSummary`：今日打卡进度。
- `EmptyState`：空数据状态。
- `LoadingState`：加载状态。
- `ErrorState`：错误状态。
- `ConfirmDialog`：确认弹窗。
- `ToastMessage`：轻量操作反馈。
- 底部导航复用微信原生 tabBar；首版不自建 `BottomTabBar`。

所有组件应统一使用设计变量控制颜色、字体、间距和圆角。

### 18.5 导航与交互规范

底部导航固定为三个一级页面：

1. 活动广场。
2. 我的打卡。
3. 我的。

导航应清晰、简洁，使用含义明确的图标和文字标签，并突出当前选中页面。

交互要求：

- 页面切换应保持流畅，不使用无必要的复杂动画。
- 按钮应具有明确的点击反馈。
- 提交后显示结果；移除活动、后台结束/停用和账号注销提供必要确认。普通加入保持轻量，手动确认首次说明不可撤销。
- 加入活动、打卡完成、投稿成功等操作应及时更新界面。
- 空列表应展示友好提示和下一步操作入口。
- 加载失败时应提供重试方式。
- 不得出现无响应的按钮或仅用于装饰的交互控件。
- 重要操作应考虑重复点击和网络异常。

### 18.6 空状态与异常状态

所有主要页面均应设计以下状态：

- 首次进入且没有数据。
- 数据加载中。
- 搜索无结果。
- 用户尚未加入任何活动。
- 今日任务全部完成。
- 活动未开始、已暂停、已结束、平台停用或核验超期。
- 游客或会话已失效。
- 服务端日期变化、结果待确认、账号注销处理中。
- 活动链接不可用。
- 投稿提交失败。
- 网络请求失败。

空状态应采用简短文案和明确的操作入口，不依赖复杂插画。

### 18.7 微信小程序适配规范

- 使用微信小程序原生支持的布局、导航及交互能力。
- 适配不同屏幕宽度，避免固定宽度导致溢出。
- 正确处理状态栏、顶部安全区域和底部安全区域。
- 底部导航及固定操作区不得遮挡页面内容。
- 长活动名称、长说明和长平台名称应支持合理换行。
- 处理系统字体、屏幕缩放和不同设备的显示差异。
- 外部活动入口应遵守微信平台相关跳转规则，不得假设所有第三方链接都可以直接打开。
- 表单应支持键盘弹出、页面滚动和提交后的状态反馈。
- 从外部返回前台时刷新服务端日期、活动可执行性和个人记录；不自动标记完成。

### 18.8 可访问性要求

- 普通文字与背景对比度至少 4.5:1，使用实际渲染背景校验。
- 核心按钮应有明确的操作名称。
- 不应只依靠颜色传达任务状态。
- 核心按钮、图标和筛选的实际点击区域至少 44×44 CSS px，可通过内边距扩展；相邻操作避免重叠。
- 对较长内容应提供合理的换行和阅读间距。

### 18.9 明确禁止的设计方式

- 小程序用户端不使用密集后台管理系统风格；本条不限制运营后台使用表格。
- 不在页面上堆叠大量数据卡片。
- 不为所有模块添加边框和阴影。
- 不使用过多渐变、装饰性图标和高饱和色。
- 不使用未经统一规范的多种圆角和字体。
- 不在首屏展示过多统计指标。
- 不为追求视觉效果而增加多余的操作步骤。
- 不使用与实际功能不符的按钮、假数据或无效交互。

### 18.10 UI 验收标准

UI 开发完成后，应满足以下条件：

1. 三个主页面具有一致的视觉语言。
2. 页面层级清晰，用户能快速找到主要功能。
3. 活动卡片、按钮、标签和导航均使用统一组件。
4. 不存在明显的文字溢出、组件重叠或安全区域遮挡。
5. 搜索、分类切换、加入活动、手动打卡、投稿入口均可实际操作。
6. 加载、空状态、异常状态均有合理展示。
7. 在 iOS、Android 各至少一台真机完成检查，覆盖窄屏、大屏、系统大字体、键盘、安全区、前后台切换和真实入口回退；模拟器只作为补充。
8. 不得仅凭截图判断交付完成，必须实际运行并检查核心交互。
9. 未实现的功能应明确标记，不得用静态界面伪装成已实现功能。
