# “打卡了吗”微信小程序产品需求文档（PRD）

**版本：** V1.0  
**日期：** 2026-10-28  
**产品形态：** 微信小程序 + 轻量运营管理后台  
**开发方式：** AI 辅助开发（Codex）

---

## 1. 产品概述

### 1.1 产品背景

各类平台会不定期提供每日签到、积分兑换、免费礼品、优惠权益和限时福利。相关入口分散在不同 App、小程序、网站或平台内部页面，用户容易忘记入口、错过有效期，也难以统一管理每天需要完成的任务。

“打卡了吗”希望将这些活动集中展示，并提供活动入口、参与说明、个人待办和手动完成记录，帮助用户更方便地发现福利、执行任务和反馈失效信息。

### 1.2 产品定位

一个由社区线索和运营审核共同维护的免费福利活动目录与个人打卡清单。产品负责整理信息、提醒用户执行和记录完成情况，不承诺活动一定可参与或一定获得奖励。

### 1.3 产品目标

1. 集中展示经过初步核验的福利活动，降低用户寻找入口的成本。
2. 将用户感兴趣的活动加入个人清单，形成每日待办。
3. 支持用户手动记录完成状态，帮助形成持续参与习惯。
4. 允许用户提交新活动、反馈失效入口，逐步扩充并维护活动库。
5. 通过小规模 MVP 验证使用频率、留存和活动内容供给，再考虑广告等变现方式。

### 1.4 非目标

首版不实现：

- 自动登录第三方平台或自动完成签到。
- 读取第三方 App/小程序中的积分、余额、签到结果或中奖状态。
- 保证活动真实性、库存、中奖概率或奖励到账。
- 复杂积分商城、用户社交、排行榜和邀请裂变。
- 未经审核的用户投稿直接公开发布。
- 自动抓取所有平台活动或大规模 AI 爬虫。
- 首版即接入广告变现；广告应在产品体验验证后再评估。

## 2. 用户与使用场景

### 2.1 目标用户

- **福利收集者：** 经常关注免费礼品、优惠券、平台积分和签到活动。
- **任务管理者：** 参加多个每日活动，希望知道今天还有哪些没完成。
- **活动贡献者：** 发现新的活动入口，愿意提交给其他用户。
- **内容运营者：** 维护活动信息、审核投稿、处理失效反馈。

### 2.2 核心用户旅程

**发现活动：** 打开活动广场 → 搜索或按分类筛选 → 查看活动详情 → 加入“我的打卡”。

**完成任务：** 打开“我的打卡” → 查看今日待办 → 跳转第三方入口 → 在第三方平台自行操作 → 返回小程序手动标记完成。

**贡献活动：** 点击“提交活动” → 填写已知信息（允许没有直达链接）→ 提交审核 → 查看审核结果。

**反馈失效：** 在活动详情点击“反馈问题” → 选择失效原因并补充说明 → 运营核验后更新状态。

## 3. 信息架构与导航

底部导航固定为三个一级页面：

1. **活动广场**：活动发现、搜索筛选、活动详情入口、提交活动入口。
2. **我的打卡**：今日待办、全部已加入活动、手动完成记录。
3. **我的**：个人数据、我的投稿、反馈记录、用户协议、隐私政策。

活动详情页、提交活动页、问题反馈页作为二级页面，从对应入口进入。

### 3.1 活动广场

页面自上而下建议包含：

- 页面标题“打卡了吗”。
- 今日待办提示，例如“今天还有 3 项待完成”。
- 搜索框：按活动名称、平台名称、关键词搜索。
- 分类筛选：全部、每日签到、免费礼品、优惠权益、限时活动。
- 活动列表：默认优先展示仍有效、近期核验、适合当前参与的活动。
- “提交活动”入口。

#### 活动卡片字段

- 活动名称。
- 所属平台。
- 活动类型标签。
- 奖励或权益摘要。
- 参与方式摘要。
- 活动期限或截止日期（如已知）。
- 状态标签：可参与、即将结束、待核验、已暂停等。
- 最近核验日期。
- 操作：查看详情、加入打卡；已加入时显示“已加入”。

#### 搜索与筛选规则

- 搜索不区分大小写；中文按名称、平台名、关键词匹配。
- 分类筛选与搜索条件可以叠加。
- 默认不向普通用户展示草稿、审核中的投稿和已驳回内容。
- 已过期活动默认从“可参与”列表隐藏；可在运营后台查询，必要时可在详情中展示“已结束”说明。
- 若无搜索结果，展示空状态和“提交活动”入口。

### 3.2 活动详情

展示以下信息：

- 活动名称、平台名称、活动类型。
- 奖励内容及限制说明。
- 参与资格或地区限制（如已知）。
- 活动开始时间、截止时间或长期有效说明。
- 参与入口类型及入口信息。
- 参与步骤（按序号展示）。
- 需要注意的规则、门槛、每日次数或兑换条件（如已知）。
- 最近核验时间和信息可信度提示。
- “加入我的打卡”按钮。
- “去参与”按钮。
- “反馈问题”按钮。

**入口类型：**

1. 直达链接：可打开的网页链接或允许使用的跳转入口。
2. 平台内搜索：展示平台名称及搜索关键词，例如在平台内搜索“成就中心”。
3. 小程序路径：展示小程序名称、路径或进入步骤；若技术上不能直接跳转，则提供复制信息或操作说明。
4. 其他方式：展示人工整理的详细说明。

如果没有可靠的直达链接，不应阻止活动发布；应要求提供足够清晰的关键词或步骤，并由运营审核。

### 3.3 我的打卡

页面分为两个区域或两个切换标签：

- **今日待办：** 今日尚未手动标记完成的活动。
- **全部已加入：** 用户加入的所有活动，可按待完成、已完成、已暂停筛选。

每条任务显示活动名称、平台、今日状态、入口按钮和完成操作。

#### 手动打卡规则

- 用户点击“去参与”后，小程序尝试打开活动入口；若无法直接跳转，则展示操作指引。
- 用户完成第三方操作后，返回小程序点击“标记完成”。
- 完成状态由用户主动确认，不代表系统已从第三方平台核实。
- 每日任务按活动配置的打卡周期重置；非每日活动按配置的任务规则处理。
- 重复点击应防止重复写入同一天的完成记录。
- 已完成任务可以展示完成时间，并按产品规则允许撤销或不允许撤销；MVP 建议不提供撤销，以减少状态歧义。
- 活动被运营暂停或标记结束后，用户仍可查看历史记录，但不应继续被列为可执行待办。

### 3.4 我的

展示：

- 用户加入的活动数。
- 累计手动打卡次数。
- 今日完成数（可选）。
- 我的投稿及其审核状态。
- 我的失效反馈及处理状态。
- 意见反馈入口。
- 用户服务协议、隐私政策。

如未登录或未建立用户身份，应使用微信小程序允许的身份能力；不应为了首版强制收集手机号、真实姓名等非必要信息。

## 4. 活动提交与内容审核

### 4.1 提交入口

活动广场和“我的”均可进入“提交活动”。提交前说明：投稿不等于立即发布，运营核验后才会展示。

### 4.2 提交表单

表单应尽量轻量，必填项控制在最少范围内。

| 字段              | 是否必填 | 控件/规则                | 说明                                     |
| ----------------- | -------- | ------------------------ | ---------------------------------------- |
| 活动名称          | 必填     | 文本，建议 2–60 字       | 用户可填写近似名称，运营可规范化         |
| 所属平台          | 必填     | 选择已有平台；支持“其他” | 例如电商平台、银行、品牌官方平台         |
| 活动类型          | 必填     | 单选                     | 每日签到、免费礼品、优惠权益、限时活动   |
| 入口方式          | 必填     | 单选                     | 直达链接、平台内搜索、小程序路径、其他   |
| 活动链接          | 条件必填 | URL 输入                 | 选择直达链接时必填；其他方式可不填       |
| 搜索关键词        | 条件必填 | 文本                     | 选择平台内搜索时必填                     |
| 参与步骤/入口说明 | 必填     | 多行文本                 | 描述从哪里进入、如何参与；建议 10–500 字 |
| 奖励摘要          | 选填     | 文本                     | 如积分、优惠券、免费试用装等             |
| 活动期限          | 选填     | 日期或文本               | 不清楚时允许留空，并提示运营核实         |
| 备注/注意事项     | 选填     | 多行文本                 | 如地区限制、会员门槛、库存限制           |
| 相关截图          | 选填     | 图片上传                 | MVP 可暂缓实现，或限制数量和大小         |

提交前进行必填校验、URL 格式校验及重复投稿提示。不要要求用户必须提供精确 URL，因为部分活动只能通过平台内搜索或多步路径进入。

### 4.3 投稿状态

- **待审核：** 已提交，普通用户不可见。
- **已通过：** 运营核验后进入活动库；可关联已有平台和活动。
- **已驳回：** 不发布，向投稿用户展示简要原因。

用户可在“我的投稿”查看状态、提交时间、处理时间及审核备注。首版不需要复杂的申诉系统。

### 4.4 运营审核流程

1. 查看投稿内容及投稿时间。
2. 检查活动是否存在、入口是否可用、步骤是否清晰。
3. 检查活动是否过期、是否存在明显误导或不合规内容。
4. 搜索现有活动，判断是新增活动还是更新已有活动。
5. 规范活动名称、平台、分类、奖励摘要和有效期。
6. 通过或驳回，并填写处理备注。
7. 通过后发布；如果无法确认，则可暂缓或要求补充信息。

## 5. 平台与活动的数据结构

采用“平台 → 活动”的两级结构。一个平台可包含多个独立活动，例如同一电商平台可同时存在每日签到、积分兑换、免费礼品活动。

### 5.1 平台实体 Platform

建议字段：

- `id`：平台唯一标识。
- `name`：平台名称。
- `logo_url`：平台图标，可为空。
- `description`：平台简介，可为空。
- `official_url`：官方入口，可为空。
- `status`：启用/停用。
- `created_at`、`updated_at`。

### 5.2 活动实体 Activity

建议字段：

- `id`：活动唯一标识。
- `platform_id`：关联平台。
- `title`：活动名称。
- `category`：活动类型枚举。
- `reward_summary`：奖励摘要。
- `eligibility`：参与资格或限制。
- `entry_type`：入口类型枚举。
- `entry_url`：直达链接，可为空。
- `search_keyword`：平台内搜索词，可为空。
- `entry_instructions`：入口说明。
- `participation_steps`：参与步骤，可用有序文本或 JSON 存储。
- `start_at`、`end_at`：活动开始、结束时间，可为空。
- `frequency`：任务频率，如每日、一次性、不定期。
- `rules_note`：规则和注意事项。
- `status`：草稿、待审核、已发布、已暂停、已结束、已驳回。
- `last_verified_at`：最近核验时间。
- `verified_by`：核验运营人员。
- `source_type`：运营录入/用户投稿/其他来源。
- `created_at`、`updated_at`。

### 5.3 用户活动关系 UserActivity

- `id`。
- `user_id`。
- `activity_id`。
- `joined_at`。
- `status`：进行中、已移除、已结束等。
- 唯一约束建议为 `user_id + activity_id`，避免重复加入。

### 5.4 打卡记录 CheckinRecord

- `id`。
- `user_id`。
- `activity_id`。
- `checkin_date`：按产品统一时区记录的日期。
- `completed_at`：用户确认完成的时间。
- `completion_source`：MVP 固定为用户手动确认。
- `created_at`。

建议对 `user_id + activity_id + checkin_date` 设置唯一约束，防止同一天重复记录。

### 5.5 投稿 Submission

- `id`、`submitter_id`。
- 投稿表单字段快照。
- `status`：待审核、已通过、已驳回。
- `reviewer_id`、`reviewed_at`、`review_note`。
- `created_at`、`updated_at`。

### 5.6 失效反馈 InvalidReport

- `id`、`user_id`、`activity_id`。
- `reason`：链接失效、活动结束、规则变化、无法参与、信息不准确、其他。
- `description`：补充说明。
- `status`：待处理、已解决、无法确认、重复反馈。
- `handled_by`、`handled_at`、`handling_note`。
- `created_at`。

### 5.7 用户与运营审计

用户身份只保留实现功能所需的最少字段。后台关键操作应记录操作人、操作类型、对象 ID、时间和变更摘要，以便追踪活动内容变化。

## 6. 失效反馈与内容维护

### 6.1 用户反馈流程

在活动详情点击“反馈问题”，选择原因并可填写说明。反馈提交后显示“已收到，核验后更新”。同一用户短时间内重复提交同一活动的相同反馈，应提示已有反馈或进行合并。

### 6.2 反馈原因

- 链接打不开或跳转错误。
- 活动已经结束。
- 活动规则发生变化。
- 不符合参与条件或实际无法参与。
- 奖励说明不准确。
- 其他问题。

### 6.3 运营处理规则

- 核验后更新活动信息和最近核验时间。
- 确认过期：将活动标记为已结束或暂停展示。
- 入口暂时异常：可先标记为待核验或暂停，避免持续误导。
- 无法确认：记录处理说明，必要时保留观察状态。
- 对同一活动的多个反馈可合并处理。

## 7. 运营管理后台

MVP 建议采用独立、轻量的 Web 管理后台，使用受控管理员账号登录。

### 7.1 功能模块

1. **数据概览：** 活动总数、已发布活动数、待审核投稿数、待处理反馈数、近 7 日新增投稿和反馈。
2. **平台管理：** 新增、编辑、停用平台；管理平台名称、图标和官方入口。
3. **活动管理：** 新增、编辑、复制、发布、暂停、结束、搜索和筛选活动。
4. **投稿审核：** 查看投稿详情、通过、驳回、填写审核意见、关联或合并已有活动。
5. **失效反馈：** 查看反馈、标记处理状态、填写处理结果。
6. **基础配置：** 活动分类、任务频率、协议和隐私政策文本。
7. **操作日志：** 查询关键数据变更记录。
8. **数据导入导出：** 可选支持 CSV 导入/导出，便于批量维护活动。

### 7.2 后台权限

- 普通用户不能访问后台。
- 管理员可管理平台、活动、投稿和反馈。
- 若后续引入审核员角色，可限制其只处理投稿与反馈，不允许管理账号和系统配置。
- 后台接口必须进行服务端权限校验，不能只依靠前端隐藏按钮。

## 8. 状态与业务规则

### 8.1 活动状态

| 状态   | 含义                 | 普通用户可见性                       |
| ------ | -------------------- | ------------------------------------ |
| 草稿   | 运营编辑中，尚未发布 | 不可见                               |
| 待审核 | 用户投稿或待核验内容 | 不可见                               |
| 已发布 | 已审核，可参与       | 可见                                 |
| 已暂停 | 暂时不建议参与       | 可显示状态提示，默认不进入推荐列表   |
| 已结束 | 活动已过期或结束     | 默认不进入可参与列表，可保留历史记录 |
| 已驳回 | 投稿不符合发布要求   | 不可见                               |

### 8.2 活动核验规则

- 每条已发布活动必须有“最近核验时间”；若无法确认，需明确标记“待核验”，不得表现为已确认有效。
- 运营可按核验时间排序，优先检查长期未更新的活动。
- 活动信息变更时更新 `updated_at`；人工核验后更新 `last_verified_at`。
- 活动是否过期优先依据明确的结束时间；没有结束时间时不能自动判定永久有效，应通过运营复核维护。

### 8.3 今日待办规则

- 今日待办 = 用户已加入、状态有效、符合任务周期且当天尚未完成的活动。
- 每日任务每天最多记录一次完成。
- 一次性活动完成后不再进入待办，但可在已完成列表查看。
- 活动结束或暂停后不再进入待办。
- 日期边界以产品服务端约定的时区为准；面向中国大陆用户时建议采用 `Asia/Shanghai`，并在数据层保持一致。

## 9. 非功能需求

### 9.1 易用性

- 首屏应能快速看到今日待办和活动列表。
- 加入活动、打开入口、标记完成等核心操作应尽量少步骤。
- 对没有直达链接的活动，必须清晰展示替代路径。
- 所有空状态、加载失败和提交结果均应提供明确提示。

### 9.2 性能与稳定性

- 常规列表和详情应在合理时间内完成加载。
- 搜索、筛选和打卡操作应提供加载状态并防止重复提交。
- 后端异常时保留用户可理解的错误提示，不暴露内部堆栈和敏感信息。
- 关键操作失败时允许用户重试。

### 9.3 隐私与安全

- 仅收集实现功能必需的数据。
- 明确说明打卡记录是用户手动确认，不是第三方平台自动核验结果。
- 用户投稿内容公开前必须经过审核。
- 对外部链接进行格式校验和安全处理；运营后台避免将未经审核的内容作为可信入口。
- 用户协议和隐私政策应说明数据收集范围、用途、存储和用户权利。
- 不在客户端存放数据库密钥、管理员密钥或其他服务端凭证。
- 依据微信小程序平台规则完成必要的类目、隐私声明、域名配置和审核流程。

## 10. 数据分析与验证指标

MVP 阶段建议记录以下事件：

- `activity_list_view`：浏览活动广场。
- `activity_search`：搜索活动。
- `activity_detail_view`：查看活动详情。
- `activity_join`：加入打卡。
- `activity_go`：点击去参与。
- `checkin_complete`：手动标记完成。
- `submission_create`：提交活动。
- `invalid_report_create`：提交失效反馈。

核心指标：

1. **活动加入率** = 加入活动的用户数 / 活动详情访问用户数。
2. **手动完成率** = 完成打卡次数 / 当日待办次数。
3. **次日留存率、7 日留存率**。
4. **投稿量及投稿通过率**。
5. **失效反馈比例** = 被反馈失效的活动数 / 已发布活动数。
6. **反馈处理时长**。
7. **“去参与”点击率** = 点击去参与次数 / 活动详情访问次数。

初期以 10–20 条经过人工核验的活动开始，先观察用户是否愿意加入、执行和持续回来，再决定是否扩大内容库或加入广告。

## 11. MVP 开发范围与迭代计划

### 阶段一：基础框架

- 建立小程序项目与后端数据模型。
- 建立平台、活动、用户活动关系、打卡记录等基础数据结构。
- 完成用户身份识别和必要的权限控制。

### 阶段二：核心用户功能

- 活动广场、搜索、分类筛选。
- 活动详情、入口说明和跳转。

### 阶段三：内容供给闭环

- 用户提交活动。
- 用户反馈活动失效。
- 我的投稿和反馈状态。
- 运营后台审核、活动维护和反馈处理。

- 测试微信登录/匿名身份方案、跳转兼容性和异常场景。

- 完善用户协议、隐私政策和内容审核机制。
- 录入并复核首批 10–20 条活动。
- 完成小范围体验测试，再提交小程序审核。

### 暂缓功能

- 广告接入和广告位优化。
- 自动提醒订阅消息（需另行确认用户授权与平台规则）。
- 个性化推荐、复杂排序算法。
- 自动采集第三方活动。
- 社区评论、点赞、排行榜。

## 12. 异常场景与处理

| 场景                 | 处理方式                                           |
| -------------------- | -------------------------------------------------- |
| 活动没有直达链接     | 展示平台名称、搜索关键词和分步说明，不阻止运营发布 |
| 外部链接无法打开     | 提示复制链接或按步骤进入；提供失效反馈入口         |
| 活动已经过期         | 标记已结束，不再进入待办和默认可参与列表           |
| 用户重复加入活动     | 不重复创建关系，提示已加入                         |
| 用户当天重复打卡     | 不重复写入记录，提示今日已完成                     |
| 投稿缺少必填字段     | 前端提示缺失字段，保留用户已填内容                 |
| 投稿与已有活动重复   | 提交前提示可能重复；后台支持合并或更新已有活动     |
| 运营尚未核验活动     | 显示待核验状态或暂不公开，不暗示其一定有效         |
| 网络异常导致提交失败 | 明确提示失败并允许重试，避免重复创建记录           |
| 用户反馈无法确认     | 标记“无法确认”，记录处理说明，不虚构处理结论       |

## 13. 验收标准

### 活动广场

- 用户可以查看已发布活动列表。
- 用户可以按活动名称或平台搜索。
- 用户可以按四种活动分类筛选。
- 列表卡片显示活动名称、平台、分类、奖励摘要和核验时间等关键信息。

### 活动详情

- 详情完整展示参与步骤、入口方式、期限和注意事项。
- 直达链接、平台内搜索和其他入口说明均有对应展示方式。
- 用户可以加入打卡清单并进入“我的打卡”。
- 用户可以提交失效反馈。

### 我的打卡

- 能区分今日待办和已完成活动。
- 用户可以手动标记完成。
- 每日任务在新的一天恢复为待办；同一天不能重复记录。
- 暂停或结束的活动不会继续出现在可执行待办中。

### 投稿与反馈

- 投稿表单支持没有直达 URL 的活动。
- 投稿默认进入待审核状态，不会立即公开。
- 用户可查看投稿审核状态。
- 用户可提交失效反馈并查看处理状态。

### 运营后台

- 管理员可以创建、编辑、暂停和结束活动。
- 管理员可以审核投稿并填写原因。
- 管理员可以处理失效反馈。
- 未授权用户无法调用管理接口。
- 关键管理操作有日志记录。

不要一次性要求 Codex 生成完整项目。建议按可验证的小步推进，每一步都要求先阅读现有代码、说明修改计划，再执行修改并运行检查。

### 推荐执行顺序

1. **项目初始化：** 确认技术栈、目录结构、环境变量和运行方式，先搭建空页面与底部导航。

3. **活动广场：** 用少量模拟数据完成列表、搜索和分类筛选。
4. **活动详情：** 完成参与说明、不同入口类型和加入活动操作。
5. **我的打卡：** 实现今日待办、完成记录和跨日规则。
6. **投稿与反馈：** 完成表单校验、提交状态和用户侧记录。
7. **运营后台：** 实现活动管理、投稿审核和反馈处理。
8. **联调与测试：** 检查权限、重复提交、跨日、失效活动、异常提示和小程序跳转。
9. **发布准备：** 检查隐私声明、协议、域名、平台审核要求及正式数据。

### 每个开发阶段的输出要求

- 列出新增或修改的文件。
- 说明实现了哪些需求以及尚未实现的部分。
- 给出运行、测试和验证步骤。
- 不得伪造接口或声称测试已通过；未实际运行的测试应明确标注。
- 不要将服务端密钥写入小程序前端代码。
- 如果技术选择存在分歧，先列出方案、成本和风险，不要默默更换技术栈。

## 16. 待确认事项

以下事项不阻碍先做原型，但正式开发前应确认：

1. **后端方案：** 采用微信云开发，还是独立后端服务。对个人 MVP，优先考虑运维负担较小的方案，但需结合现有技术能力和部署要求决定。
2. **身份方案：** 是否仅使用微信身份标识，还是允许游客浏览、登录后同步打卡数据。
3. **活动提醒：** 首版只显示小程序内待办，还是后续申请订阅消息提醒。
4. **截图上传：** 是否首版就允许投稿附图，或先以文字说明为主。
5. **历史活动：** 结束活动是否对普通用户保留可查历史记录。
6. **广告策略：** 在留存与体验验证后再确定广告形式、频次和展示位置。
7. **内容规范：** 明确不收录涉嫌诈骗、诱导分享、违法违规、要求提供不必要敏感信息或无法核实来源的活动。

## 17. 产品原则总结

- **先有用，再变现：** 先验证用户是否真的用它管理福利活动。
- **人工核验优先：** 先用少量高质量活动建立信任，不追求首版活动数量。
- **入口说明优先于强制链接：** 允许通过平台内搜索和操作步骤进入活动。
- **用户手动确认：** 明确区分小程序中的手动打卡记录与第三方平台的真实完成状态。
- **审核后发布：** 投稿和反馈构成内容维护闭环，但不能让未经核验的信息直接成为公开内容。
- **小步开发：** 先完成活动发现、加入、手动打卡这条核心闭环，再逐步扩展运营和变现能力。

# 18. UI/UX 设计规范与开发约束

## 18.1 设计目标

本项目采用 Apple iOS 原生应用的极简设计语言，结合微信小程序的运行环境和交互规范，构建简洁、精致、易用的用户界面。

设计核心原则：

1. **极简主义：** 减少不必要的装饰、边框、阴影和视觉元素，突出活动内容与核心操作。
2. **内容优先：** 活动名称、奖励信息、参与步骤、打卡状态应具有清晰的视觉层级。
3. **轻量交互：** 用户应能够快速完成浏览、加入打卡、手动确认和活动投稿。
4. **统一规范：** 全部页面使用统一的色彩、字体、间距、圆角和组件样式。
5. **自然反馈：** 按钮点击、任务完成、投稿成功等操作应提供简洁明确的反馈。
6. **移动端优先：** 优先适配常见 iPhone 屏幕尺寸，同时兼容其他微信小程序支持的设备。

整体风格应接近 iOS 原生应用的简洁、精致与秩序感，但不得直接复制 Apple 官方产品的专有界面或品牌元素。

## 18.2 视觉设计规范

### 18.2.1 色彩系统

采用低饱和度中性色作为基础，使用克制的蓝色作为主要交互色。

| 用途     | 色彩值    | 设计说明                     |
| -------- | --------- | ---------------------------- |
| 页面背景 | `#F5F5F7` | 浅灰白色，降低视觉负担       |
| 卡片背景 | `#FFFFFF` | 保持内容清晰、干净           |
| 主文字   | `#1D1D1F` | 用于页面标题、活动名称       |
| 次级文字 | `#86868B` | 用于辅助说明、时间、备注     |
| 主强调色 | `#007AFF` | 用于主要按钮、链接、选中状态 |
| 成功状态 | `#34C759` | 用于打卡完成、操作成功       |
| 提醒状态 | `#FF9F0A` | 用于即将截止、需要关注       |
| 错误状态 | `#FF3B30` | 用于错误提示、操作失败       |
| 分隔线   | `#E5E5EA` | 用于列表分隔和轻量边界       |

设计约束：

- 页面中以白色、浅灰色和深色文字为主。
- 强调色仅用于必要的交互元素，不应大面积铺设。
- 不使用多色渐变作为默认背景。
- 不使用大面积高饱和色块装饰页面。
- 不应仅通过颜色区分活动状态，还应提供文字或图标说明。

### 18.2.2 字体规范

优先使用系统默认无衬线字体，保证中文在 iOS 和 Android 设备上的自然显示。

建议层级：

| 元素         | 字号建议 | 字重     |
| ------------ | -------: | -------- |
| 页面主标题   |  26–30px | Semibold |
| 区块标题     |  18–20px | Semibold |
| 活动名称     |  16–17px | Medium   |
| 正文内容     |  14–16px | Regular  |
| 辅助说明     |  12–13px | Regular  |
| 按钮文字     |  15–16px | Medium   |
| 数据统计数字 |  28–36px | Semibold |

以上尺寸为设计参考，应结合微信小程序实际布局调整。开发时优先使用统一的字号变量，不得在各页面随意设置字体大小。

### 18.2.3 间距与布局

建立统一的间距体系：

- 页面左右边距：16–20px。
- 卡片内部间距：16px。
- 主要区块之间：24–32px。
- 同一组内相关元素间距：8–12px。
- 页面底部应考虑安全区域和底部导航栏高度。

所有页面应遵循统一的对齐规则。优先使用清晰的垂直布局、自然留白和规整的信息分组。

### 18.2.4 圆角、边框与阴影

- 普通卡片圆角：16–20px。
- 按钮圆角：12–16px。
- 标签圆角：采用胶囊形或轻圆角。
- 输入框圆角：12px 左右。
- 分割线使用低对比度浅灰色。
- 默认卡片不使用明显阴影。
- 弹窗和浮层仅使用轻微阴影区分层级。

禁止为每一个信息区域都添加独立边框，避免出现传统后台系统的密集卡片风格。

## 18.3 三个主页面的 UI 规范

### 18.3.1 活动广场

**页面定位：发现福利活动。**

采用清爽的内容浏览布局。

页面从上到下依次为：

1. 页面标题「打卡了吗」，搭配简短的欢迎文案。
2. 今日待办摘要，显示今日尚未完成的打卡数量。
3. 搜索框，支持搜索平台名称和活动名称。
4. 活动分类切换：全部、每日签到、免费礼品、优惠权益、限时活动。
5. 活动列表，使用统一的简洁活动卡片。
6. 提交活动入口。

活动卡片应包含：

- 平台名称或图标。
- 活动名称。
- 一句话奖励说明。
- 活动类型标签。
- 截止时间或最近核验时间（如有）。
- 加入打卡或已加入状态。

卡片应以文字信息为主体，不要求每项活动都使用封面大图。

活动卡片的主要操作应明确，但避免同时出现过多按钮。用户点击卡片进入详情页，点击主要操作即可加入打卡清单。

### 18.3.2 我的打卡

**页面定位：管理每日任务。**

该页面应突出任务完成情况，而不是复杂的统计图表。

页面结构：

1. 页面标题「我的打卡」。
2. 今日进度，例如「今日已完成 3 / 5 项」。
3. 简洁的进度条。
4. 待完成、已完成两个状态切换。
5. 用户加入的活动列表。

每项任务展示：

- 活动名称和所属平台。
- 当前任务状态。
- 打开活动的操作入口。
- 手动确认完成的操作。
- 必要的参与说明。

交互规则：

- 用户可先打开外部活动页面，再返回小程序手动确认完成。
- 完成任务后，进度与任务状态应即时更新。
- 已完成任务应采用弱化显示的方式，避免干扰未完成任务。
- 重复点击完成操作不得重复创建同一日期的打卡记录。
- 每日任务应按日期重新计算完成状态，历史记录应保留。

### 18.3.3 我的

**页面定位：展示用户信息和个人记录。**

采用简洁的个人中心布局，不使用传统管理后台式菜单。

页面结构：

1. 用户头像及昵称；没有必要时允许使用默认头像。
2. 核心数据摘要：已加入活动数、累计打卡次数。
3. 我的投稿。
4. 我的失效反馈。
5. 意见反馈。
6. 用户服务协议与隐私政策。

数据摘要可采用横向排列的轻量数字模块，不应设计成占据大量空间的大型统计卡片。

不强制收集手机号、真实姓名等非必要个人信息。

## 18.4 通用组件规范

开发时应建立可复用的组件，避免三个页面重复实现相似样式。

建议至少包括：

- `PageHeader`：统一页面标题。
- `ActivityCard`：活动卡片。
- `CategoryTabs`：活动分类切换。
- `StatusTag`：活动状态标签。
- `PrimaryButton`：主要操作按钮。
- `SearchBar`：搜索框。
- `ProgressSummary`：今日打卡进度。
- `EmptyState`：空数据状态。
- `LoadingState`：加载状态。
- `ErrorState`：错误状态。
- `ConfirmDialog`：确认弹窗。
- `ToastMessage`：轻量操作反馈。
- `BottomTabBar`：底部导航。

所有组件应统一使用设计变量控制颜色、字体、间距和圆角。

## 18.5 导航与交互规范

底部导航固定为三个一级页面：

1. 活动广场。
2. 我的打卡。
3. 我的。

导航应清晰、简洁，使用含义明确的图标和文字标签，并突出当前选中页面。

交互要求：

- 页面切换应保持流畅，不使用无必要的复杂动画。
- 按钮应具有明确的点击反馈。
- 提交、删除、移除活动等重要操作应提供必要的确认或结果提示。
- 加入活动、打卡完成、投稿成功等操作应及时更新界面。
- 空列表应展示友好提示和下一步操作入口。
- 加载失败时应提供重试方式。
- 不得出现无响应的按钮或仅用于装饰的交互控件。
- 重要操作应考虑重复点击和网络异常。

## 18.6 空状态与异常状态

所有主要页面均应设计以下状态：

- 首次进入且没有数据。
- 数据加载中。
- 搜索无结果。
- 用户尚未加入任何活动。
- 今日任务全部完成。
- 活动已结束或已暂停。
- 活动链接不可用。
- 投稿提交失败。
- 网络请求失败。

空状态应采用简短文案和明确的操作入口，不依赖复杂插画。

## 18.7 微信小程序适配规范

- 使用微信小程序原生支持的布局、导航及交互能力。
- 适配不同屏幕宽度，避免固定宽度导致溢出。
- 正确处理状态栏、顶部安全区域和底部安全区域。
- 底部导航及固定操作区不得遮挡页面内容。
- 长活动名称、长说明和长平台名称应支持合理换行。
- 处理系统字体、屏幕缩放和不同设备的显示差异。
- 外部活动入口应遵守微信平台相关跳转规则，不得假设所有第三方链接都可以直接打开。
- 表单应支持键盘弹出、页面滚动和提交后的状态反馈。

## 18.8 可访问性要求

- 文字与背景应具有足够的对比度。
- 核心按钮应有明确的操作名称。
- 不应只依靠颜色传达任务状态。
- 点击区域应足够大，避免小图标难以操作。
- 对较长内容应提供合理的换行和阅读间距。

## 18.9 明确禁止的设计方式

- 不使用传统后台管理系统风格。
- 不在页面上堆叠大量数据卡片。
- 不为所有模块添加边框和阴影。
- 不使用过多渐变、装饰性图标和高饱和色。
- 不使用未经统一规范的多种圆角和字体。
- 不在首屏展示过多统计指标。
- 不为追求视觉效果而增加多余的操作步骤。
- 不使用与实际功能不符的按钮、假数据或无效交互。

## 18.10 UI 验收标准

UI 开发完成后，应满足以下条件：

1. 三个主页面具有一致的视觉语言。
2. 页面层级清晰，用户能快速找到主要功能。
3. 活动卡片、按钮、标签和导航均使用统一组件。
4. 不存在明显的文字溢出、组件重叠或安全区域遮挡。
5. 搜索、分类切换、加入活动、手动打卡、投稿入口均可实际操作。
6. 加载、空状态、异常状态均有合理展示。
7. 在至少两种不同尺寸的设备或模拟器中完成布局检查。
8. 不得仅凭截图判断交付完成，必须实际运行并检查核心交互。
9. 未实现的功能应明确标记，不得用静态界面伪装成已实现功能。
